Under the native engine, React Native libraries' own Jest support runs with Jest's module semantics. A library's setup file or mock (`react-native-gesture-handler/jestSetup`, `react-native-safe-area-context/jest/mock`, `react-native-reanimated/mock`) gets a `jest` of its own: `jest.mock` reaches every `require` of the module, `jest.requireActual` and `@jest/globals` work, and an implementation the library installs while building its mocks survives `vi.resetAllMocks()` and `mockReset: true` (where Jest's `resetMocks` would drop it). What a library's setup registers lasts as long as its module: each test file loads it afresh by default and under the hot runtime, and under `isolate: false` a setup file's library mocks reach every file, as the module itself does. A setup file is served whether it is required, imported or listed in `setupFiles`, and so is one of a workspace library linked from outside node_modules; the project's own files named `mock` or under a `jest/` directory are not given a library's `jest`. Before, a suite migrated from Jest that imported such a setup file ran it with Vitest's `vi`, whose `mock` never reaches Node's `require`, so it changed nothing. Nothing is put on the global `jest`.

`jest.requireActual` of a package a preset shadows is the package, as under Jest; it was the preset.

Under the native engine, these presets are their library's own mock, as a Jest suite installs it, matching Jest on every probe of an Expo SDK 58 app but the one noted:

- `react-native-worklets` is Worklets' `lib/module/mock.js`. The real package's JS implementation fails every test file with react-native-gesture-handler 3 ("`getUIRuntimeHolder` is not supported on web"), under Jest as well. `runOnJS`, `runOnUI`, `scheduleOnRN` and `scheduleOnUI` behave as under Jest with that mock; the preset ran them synchronously.
- `react-native-safe-area-context` is its `jest/mock`: insets are zero on a 320×640 frame (the preset gave 47/34 on 390×844) unless `<SafeAreaProvider initialMetrics>` gives metrics, which the preset ignored, and `useSafeAreaInsets` and `useSafeAreaFrame` are mock functions. `setInsets()` now sets what `useSafeAreaInsets` returns, until `resetAllMocks()`, and no longer reaches `SafeAreaInsetsContext`, `withSafeAreaInsets` or `initialWindowMetrics`; `<SafeAreaProvider initialMetrics>` gives every consumer the same insets. A suite's own `jest.mock('react-native-safe-area-context', () => ({ ...jest.requireActual('react-native-safe-area-context'), ... }))` now spreads the real package, as under Jest, whose `SafeAreaProvider` renders nothing until native metrics arrive.
- `react-native-keyboard-controller`, `@gorhom/bottom-sheet` and `@react-native-community/netinfo` are their own Jest mocks (`jest`, `mock`, `jest/netinfo-mock.js`): keyboard-controller's hooks return React Native `Animated.Value`s and are mock functions, bottom-sheet's views render their children and nothing of their own (a `BottomSheetView`'s `testID` is not on the tree), and netinfo rests on a connected cellular network, each as under Jest. One difference is deliberate: bottom-sheet's default import is its `BottomSheet` component, where Jest's interop hands a suite the mock's whole module object, which does not render.

A package naming different files in its `react-native` field and its `main` is one module whether imported or required: a bare `require` now resolves the `react-native` field, as Metro and an `import` do, where it read `main` and loaded a second copy (`react-native-worklets` was loaded twice). With Reanimated 4.7 or later, its test helpers `withReanimatedTimer` and `advanceAnimationByTime` work without the jest-compat layer.
