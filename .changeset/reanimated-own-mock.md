Under the native engine, `react-native-reanimated` is Reanimated's own test mock (`react-native-reanimated/mock`), as a Jest suite gets it with `jest.mock('react-native-reanimated', () => require('react-native-reanimated/mock'))`. The hand-written preset lacked 104 of the names that mock provides (`interpolateColor`, `clamp`, `Keyframe`, `useScrollOffset`, `Extrapolate`, most layout animation presets, `Easing.exp`/`bounce`/`elastic`, and its test helpers `withReanimatedTimer` and `getAnimatedStyle`), and called animation callbacks with `{ finished, current }` where Reanimated passes `true`, so `if (finished)` code paths did not run as on a device. On an Expo SDK 58 app, every probe of reanimated matches Jest with Reanimated's mock except `Animated.View`'s shape, which wraps real React Native's `View`.

The mock loads the real package and `react-native-worklets` in their JS implementations, through the Jest resolvers both libraries ship (`react-native-reanimated/jest/resolver`), which the native engine now applies to their files. So under the native engine the worklets preset no longer applies: `runOnJS`, `runOnUI`, `scheduleOnRN` and `scheduleOnUI` run their worklet on a later tick, as the real package does under Jest, where the preset ran it synchronously; a test that reads the result awaits it (`await waitFor(...)`). `presets: { worklets: true }` keeps the preset there. A suite that wants the real Reanimated instead turns the preset off with `presets: { reanimated: false }`, and the real package then runs in its JS implementation. The mock engine keeps both presets.
